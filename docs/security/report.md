## Threat Model

Fahrtwerk is an internal municipal Laravel application for personal vehicle/trip records, reimbursement submission and approval, reports, exports, and audited administration. User-provided deployment context: one central Docker deployment on an internal network; EMPLOYEE access is personal and ADMIN access organization-wide. Browser requests enter Nginx, then PHP-FPM/Laravel controllers and services, then PostgreSQL; separate Docker volumes hold database data, application storage, and the database password (routes/web.php:29; routes/web.php:48; docker/nginx.conf:15; docker/nginx.conf:20; docker-compose.yml:14; docker-compose.yml:35). Production startup generates missing application/database secrets, migrates, bootstraps an administrator, and caches views (docker/app-entrypoint.sh:5; docker/app-entrypoint.sh:17; docker/postgres-entrypoint.sh:4). The test Compose deployment uses a separate ephemeral PostgreSQL database with trust authentication and array session/cache stores; it is not the production authorization boundary (docker-compose.test.yml:9; docker-compose.test.yml:10; docker-compose.test.yml:20). A scheduler service runs the same app image with php artisan schedule:work after app health, sharing application storage and the read-only secret mount; a minute heartbeat supports its healthcheck (docker-compose.yml:65; docker-compose.yml:76; docker-compose.yml:78; docker-compose.yml:84; routes/console.php:69).

### Trust Boundaries

- Network client to web application: production publishes ${APP_BIND:-127.0.0.1}:${APP_PORT:-8080}:80. Nginx forwards only index.php to app:9000, denies other PHP, dot paths and /storage, disables access logging and caps request bodies at 3m. The network named internal is declared as a bridge, without an internal:true declaration; the database has no published port. Internal-network restriction and any HTTPS termination beyond this default remain operator responsibilities (docker-compose.yml:23; docker-compose.yml:54; docker-compose.yml:95; docker/nginx.conf:8; docker/nginx.conf:9; docker/nginx.conf:16; docker/nginx.conf:23).
- Anonymous visitor to authenticated user: local authentication requires active=true; login is limited by username/IP and IP counters, regenerates the session, and records auth_version. The ready middleware rejects inactive or version-mismatched accounts and enforces initial password/profile completion. Logout invalidates the session; password reset increments auth_version and deletes stored sessions (app/Services/LocalAuthenticator.php:12; app/Http/Controllers/AuthController.php:25; app/Http/Controllers/AuthController.php:35; app/Http/Middleware/EnsureAccountReady.php:14; app/Services/UserService.php:25).
- Browser-origin and response confidentiality boundary: routes use Laravel's web routing integration; the custom configuration adds security headers and does not declare CSRF exceptions. Session defaults are database, 120 minutes, HttpOnly and SameSite=Lax; session encryption defaults false in config but true in .env.example, while Secure is environment-controlled. CSP restricts scripts/forms and framing, sensitive responses are no-store, and HSTS is conditional on isSecure() (bootstrap/app.php:12; bootstrap/app.php:13; config/session.php:21; config/session.php:35; config/session.php:50; config/session.php:172; config/session.php:185; config/session.php:202; .env.example:30; app/Http/Middleware/SecurityHeaders.php:12).
- EMPLOYEE to another employee's records: active owner-or-admin policies protect individual trips, vehicles, templates and settlements; TripQuery scopes non-admin lists/reports/exports by user_id. Profile updates operate on the current user with an explicit personal-field allowlist. Vehicle assignment for trips is constrained to the owner and reinforced by a PostgreSQL composite foreign key (app/Providers/AppServiceProvider.php:29; app/Policies/OwnedRecordPolicy.php:12; app/Services/TripQuery.php:15; app/Http/Controllers/ProfileController.php:18; app/Services/TripService.php:33; database/migrations/2026_09_09_000001_create_fahrtwerk_tables.php:163).
- Authenticated user to ADMIN capabilities: active ADMIN middleware protects account/master-data/settings/audit/import routes and settlement transitions. Administrators can create/reset credentials and assign EMPLOYEE/ADMIN roles; self-demotion and removal of the last active admin are blocked. Returned credentials are delivered in the authenticated admin response, separately from operator-only credential files (routes/web.php:45; routes/web.php:48; app/Http/Middleware/EnsureAdmin.php:11; app/Http/Controllers/Admin/UserController.php:46; app/Http/Controllers/Admin/UserController.php:49; app/Http/Controllers/Admin/UserController.php:59; app/Http/Controllers/Admin/UserController.php:74).

Settlement transitions use an explicit state machine; approval creates immutable values and identity snapshots. Critical status/correction audit events are written inside transactions. - ADMIN CSV input to organization-wide trip creation: uploads are limited to 2 MiB CSV/text, 40 columns and 1,000 rows; generated local tokens are bound to current session user and a 30-minute expiry. ### Attacker Capabilities

- An unauthenticated client able to reach the published HTTP service can request public login and health endpoints and submit login inputs, but has no established account, application session, DB connection or host authority (routes/web.php:19; routes/web.php:25; docker-compose.yml:54).
- An authenticated EMPLOYEE controls their own profile and eligible trip/vehicle/template inputs, filters, submitted identifiers and browser requests. They do not start with another employee's data, ADMIN capabilities, local file access, APP_KEY, or Docker/DB authority (app/Http/Controllers/ProfileController.php:18; app/Policies/OwnedRecordPolicy.php:12; app/Services/TripQuery.php:15).
- An authenticated ADMIN legitimately accesses organization-wide records, credential issuance, rules/settings, import, approval and audit views. They do not legitimately gain untraceable historical mutations, modification of immutable financial snapshots, filesystem/DB console access or host execution merely from that web role (routes/web.php:48; app/Services/SettlementService.php:52; database/migrations/2026_09_09_000001_create_fahrtwerk_tables.php:169).
- A hostile CSV or logo producer controls bytes subsequently uploaded by an authorized admin; their influence is through bounded parsing/validation and generated server-side resource identifiers, not an assumed right to choose local filesystem paths (app/Http/Controllers/Admin/ImportController.php:19; app/Services/ImportService.php:17; app/Http/Controllers/Admin/SettingsController.php:22).
- Docker-host administrators already possess backup, restore, secret and container authority. A claim requiring those privileges is not a gain across the ordinary EMPLOYEE/ADMIN boundary (scripts/backup.sh:9; scripts/restore.sh:13).

### Security Objectives

- User requirement: EMPLOYEE may access only their own personal data; ADMIN may access organization-wide data. Preserve owner restrictions consistently in individual-object, list, report, export, and relational assignment paths.
- User requirement: no untraceable historical changes and immutable financial snapshots, including for ADMIN. Preserve transactional audit and state transitions, correction reasons, versioned rates, snapshot values and PostgreSQL history triggers (app/Services/TripService.php:56; app/Services/SettlementService.php:68; database/migrations/2026_09_09_000001_create_fahrtwerk_tables.php:169).
- User requirement: no secrets in the repository or logs. Secret-bearing paths are excluded from Git/build context, credentials are stored privately or shown only through authorized issuance workflows, and Audit excludes password/token/version fields. These controls are not a proof that all exception logging paths redact secrets (.gitignore:1; .gitignore:10; .dockerignore:2; .dockerignore:9; app/Services/Audit.php:15; bootstrap/app.php:19).
- User requirement: central Docker-only deployment on an internal network. Keep DB unpublished, preserve loopback default or explicitly controlled internal interface exposure, and distinguish production settings from the test-only trust-auth deployment (docker-compose.yml:23; docker-compose.yml:54; docker-compose.test.yml:9).
- Keep authentication/session lifecycle and credential reset authority effective; protect availability using the configured 2 MiB upload, 3 MiB request, 256 MiB PHP memory, 120-second PHP execution, 12 FPM-worker and bounded import limits (app/Http/Controllers/AuthController.php:27; app/Services/UserService.php:25; docker/php.ini:5; docker/php.ini:8; docker/fpm.conf:7; app/Services/ImportService.php:17).

### Assumptions

- User context defines an internal municipal deployment; actual host networking, HTTPS termination, firewall rules, backup permissions and runtime environment values were not supplied or inspected. Actual .env credential material and vendor/.tools were excluded.
- Source-backed default/claim distinction: the network is named internal but only driver: bridge is configured. Default web binding is loopback; neither the network name nor lack of a DB host port establishes network-level egress isolation or the actual deployed client perimeter (docker-compose.yml:54; docker-compose.yml:95).
- Effective environment is unresolved. Compose loads .env and explicitly overrides DB_CONNECTION=pgsql and DB_PASSWORD_FILE. .env.example proposes DB_HOST=db, encrypted database sessions and stderr logs, while config defaults differ; example values must not be reported as observed production values (docker-compose.yml:29; docker-compose.yml:31; .env.example:20; .env.example:30; .env.example:58; config/session.php:50; config/logging.php:22).
- DB_URL is exposed as a PostgreSQL configuration input alongside discrete host/database/password values; its framework-level override semantics were not inspected because vendor code is excluded. An operator-set DB_URL could materially affect the actual destination; report it as an unresolved configuration input rather than assuming the Compose db service (config/database.php:89).
- History triggers and composite owner/status constraints are conditional on pgsql. Production Compose forces pgsql; other Laravel-configured DB drivers do not receive those PostgreSQL protections. No runtime execution verified applied migrations or deployed database privileges (docker-compose.yml:31; database/migrations/2026_09_09_000001_create_fahrtwerk_tables.php:160). The added vehicle-history trigger is likewise conditional on pgsql (database/migrations/2026_09_09_000002_harden_record_integrity.php:13).
- Source-backed cleanup update: cleanup is scheduled hourly and the production Compose now includes a scheduler service running php artisan schedule:work after app health. It shares private storage and DB credentials, removes imports older than one hour and expired database sessions, and emits a minute heartbeat even in maintenance mode. The healthcheck verifies a heartbeat younger than 180 seconds. Import session expiry does not itself remove stored bytes; cleanup still depends on this service actually running. No deployment execution was performed in this architecture pass (routes/console.php:60; routes/console.php:68; routes/console.php:69; docker-compose.yml:65; docker-compose.yml:76; docker-compose.yml:78; docker-compose.yml:84).
- Source-backed backup/restore distinction: backup creates database.dump, storage.tar.gz, secrets.tar.gz and optional environment.env. Restore consumes only database.dump and storage.tar.gz; recovery of corresponding DB secret/environment is an operator prerequisite not implemented by that script (scripts/backup.sh:9; scripts/backup.sh:12; scripts/restore.sh:9; scripts/restore.sh:14).
- Noncritical audit is configurable off, while critical history/status/settings/reset events explicitly remain audited. The broader user requirement against untraceable historical changes requires assessing which records qualify as history; ordinary profile/vehicle/template updates use noncritical audit (app/Services/Audit.php:12; app/Http/Controllers/ProfileController.php:18; app/Http/Controllers/VehicleController.php:81; app/Http/Controllers/TemplateController.php:50).
- Framework CSRF behavior, local-disk serve=true behavior, exception redaction and dependency internals were not independently audited. The first-party code uses web routing, private storage and an Nginx /storage deny rule; those facts should not be inflated into exhaustive framework assurance (bootstrap/app.php:12; config/filesystems.php:36; docker/nginx.conf:25).
- Architecture mapping is not completed vulnerability coverage. All cited source files and line bounds were checked; no application code, test suite, external services, product-source edits or additional scans were used.
